# Признаки классических временных срезов

Этот файл описывает признаки, создаваемые скриптом
[`build_classic_snapshots.py`](build_classic_snapshots.py), их формулы,
риски утечки данных и возможность использования в production.

Текущая версия генератора создаёт:

- 629 модельных признаков;
- `user_id` — технический идентификатор;
- `cutoff_date` — дата среза;
- `target` — только для размеченных срезов.

В `competition_test.parquet` столбца `target` нет.

## 1. Временная схема

Одна строка итогового датасета соответствует состоянию одного пользователя
на дату `cutoff`.

Все признаки используют только события, для которых:

```text
event_date <= cutoff
```

Для обучающих срезов целевая переменная вычисляется отдельно:

```text
target = sum(gmv)
         для cutoff + 1 ... cutoff + 30 включительно
```

Таким образом, день `cutoff` входит в признаки, но не входит в `target`.

Основные исторические окна:

```text
N ∈ {7, 14, 30, 60, 90, 180, 270}
```

Окно `N` включает `N` календарных дней:

```text
[cutoff - (N - 1), cutoff]
```

## 2. Обозначения формул

### Безопасное деление

Во всех отношениях используется функция:

```text
R(a, b) = a / b, если b != 0
R(a, b) = 0,     если b == 0
```

Нулевой знаменатель не заменяется единицей. Это важно для денежных значений
меньше единицы и для корректного различения отсутствия события.

### Симметричное изменение

Для сравнения двух периодов используется:

```text
B(recent, previous) =
    (recent - previous)
    / (abs(recent) + abs(previous) + 1)
```

Для неотрицательных показателей значение обычно лежит около диапазона
`[-1, 1]`:

- больше нуля — показатель вырос;
- около нуля — почти не изменился;
- меньше нуля — показатель снизился.

### Статус production

| Статус | Значение |
|---|---|
| ✅ | Можно рассчитывать в production на момент `cutoff` |
| ⚠️ | Можно использовать при соблюдении дополнительных условий |
| ⛔ | Нельзя подавать модели как обычный production-признак |

## 7. Волатильность дневного поведения

Для каждого окна `{N}` отсутствующие календарные дни считаются нулевыми.

Промежуточные суммы квадратов:

```text
sum_gmv_sq      = sum(daily_gmv^2)
sum_items_sq    = sum(daily_items_bought^2)
sum_searches_sq = sum(daily_searches^2)
```

Они используются для формул, но удаляются из итогового датасета.

```text
daily_mean(x, N) = sum(x) / N

daily_var(x, N) =
    max(sum(x^2) / N - daily_mean(x, N)^2, 0)

daily_std(x, N) = sqrt(daily_var(x, N))
```

| Признак | Формула | Production |
|---|---|---|
| `daily_gmv_std_{N}d` | стандартное отклонение дневного GMV | ✅ |
| `daily_gmv_cv_{N}d` | `R(daily_gmv_std, daily_gmv_mean + 1)` | ✅ |
| `daily_items_bought_std_{N}d` | стандартное отклонение дневных товаров | ✅ |
| `daily_searches_std_{N}d` | стандартное отклонение дневных запросов | ✅ |
| `max_daily_gmv_share_{N}d` | `R(max_daily_gmv, gmv)` | ✅ |

Здесь `N` — число календарных дней, а не число записанных строк. Это позволяет
учесть полные дни без событий, не разворачивая разреженный датасет до полной
сетки `user × date`.

## 9. Recency, первая дата и длина истории

Все признаки этого раздела используют последние 270 дней.

Тип события `{event}`:

```text
activity, order, cart, search, cat,
search_cart, search_order, cat_cart, cat_order
```

Для каждого типа события:

```text
days_since_last_{event}_270d =
    min(cutoff - event_date)

days_since_first_{event}_270d =
    max(cutoff - event_date)

{event}_span_270d =
    max(days_since_first - days_since_last, 0)

never_{event}_270d =
    1, если такого события в окне не было, иначе 0
```

Если события не было:

```text
days_since_last = 271
days_since_first = 0
span = 0
never = 1
```

Статус: ✅/⚠️. Признаки доступны в production, но только при наличии
согласованной 270-дневной истории. Они описывают первую дату **внутри окна
270 дней**, а не первую дату за всю жизнь пользователя.

Поздно приехавшие события способны изменить recency задним числом. Поэтому
для production-счёта желательно использовать закрытый дневной срез или
зафиксированный SLA задержки данных.

## 13. Экспоненциально затухающие признаки

Для периода полураспада:

```text
H ∈ {7, 14, 30, 60, 90}
```

и показателя:

```text
x ∈ {gmv, items_bought, items_added_to_cart, searches, activity}
```

используется вес события:

```text
weight(days_ago, H) = 0.5^(days_ago / H)

decay_x_halflife_{H}d = sum(x_day * weight(days_ago, H))
```

Статус: ✅. В production значение можно поддерживать инкрементально, ежедневно
умножая накопленное состояние на `0.5^(1/H)` и добавляя новые события.

Риски:

- timestamp события должен быть доступен на момент расчёта;
- late events меняют значение задним числом;
- формула затухания должна совпадать между train и serving.

## 14. Непересекающиеся 30-дневные блоки

Создаются девять блоков по 30 дней:

```text
k ∈ {0, 1, ..., 8}
```

```text
block_0: cutoff - 29  ... cutoff
block_1: cutoff - 59  ... cutoff - 30
...
block_8: cutoff - 269 ... cutoff - 240
```

`block_0` — самый свежий блок. Блоки не пересекаются и соответствуют длине
будущего горизонта `target`.

Для каждого блока сохраняются:

```text
gmv_block_{k}_30d
items_bought_block_{k}_30d
order_days_block_{k}_30d
items_added_to_cart_block_{k}_30d
searches_block_{k}_30d
active_days_block_{k}_30d
```

Статус: ✅. Утечки нет: даже `block_0` заканчивается в `cutoff`.

## 15. Статистики 30-дневных блоков

Для каждой метрики блоков `{metric}`:

```text
gmv, items_bought, order_days,
items_added_to_cart, searches, active_days
```

создаются:

| Признак | Формула/смысл | Production |
|---|---|---|
| `{metric}_block_mean` | среднее девяти блоков | ✅ |
| `{metric}_block_std` | стандартное отклонение блоков | ✅ |
| `{metric}_block_min` | минимум | ✅ |
| `{metric}_block_max` | максимум | ✅ |
| `{metric}_nonzero_blocks` | число блоков со значением `> 0` | ✅ |
| `{metric}_zero_block_share` | `1 - nonzero_blocks / 9` | ✅ |
| `{metric}_positive_block_mean` | среднее только ненулевых блоков | ✅ |
| `{metric}_block_slope` | линейный тренд блоков | ✅ |
| `{metric}_block_ewm` | взвешенное среднее с большим весом свежих блоков | ✅ |
| `{metric}_recent_to_block_mean` | `(block_0 + 1)/(block_mean + 1)` | ✅ |
| `{metric}_recent_zero_block_run` | число последовательных нулевых блоков от `block_0` назад | ✅ |

Формула slope:

```text
weights = [4, 3, 2, 1, 0, -1, -2, -3, -4]

block_slope = sum(block_k * weights_k) / sum(weights_k^2)
```

Положительное значение означает рост в сторону более свежих блоков.

Формула EWM:

```text
raw_weight_k = 0.75^k
weight_k = raw_weight_k / sum(raw_weight)
block_ewm = sum(block_k * weight_k)
```

Эти признаки особенно полезны для zero-inflated target: они отделяют стабильно
непокупающих пользователей от пользователей с временной паузой.

## 17. Сглаженные отношения активности

```text
items_trend_30_180 =
    (items_bought_30d + 1)
    / (items_bought_180d / 6 + 1)

gmv_trend_30_180 =
    (gmv_30d + 1)
    / (gmv_180d / 6 + 1)

items_trend_90_180 =
    (items_bought_90d + 1)
    / (items_bought_180d / 2 + 1)

gmv_trend_90_180 =
    (gmv_90d + 1)
    / (gmv_180d / 2 + 1)
```

Число `6` появляется из `180 / 30`, а `2` — из `180 / 90`.
Прибавление единицы сглаживает пользователей с нулевой историей.

Статус: ✅.

Генератор не обучает BG/NBD или Gamma-Gamma, но создаёт достаточные

| Признак | Формула/смысл | Production |
|---|---|---|
| `is_seen_270d` | `1 - never_activity_270d` | ✅ |
| `btyd_frequency_270d` | `max(order_days_270d - 1, 0)` | ✅ |

| `btyd_T_270d` | `days_since_first_order_270d` | ⚠️ |

### Ожидаемый GMV из недавней корзины

```text
expected_gmv_from_recent_cart_30d =
    items_added_to_cart_30d
    * R(items_bought_180d, items_added_to_cart_180d)
    * R(gmv_180d, items_bought_180d)
```

Интерпретация: объём недавней корзины умножается на историческую вероятность
перехода корзины в купленный товар и исторический GMV на товар.

```text

    searches_30d

    * R(gmv_search_180d, search_items_bought_180d)
```

Статус: ✅. Это эвристики, а не гарантированные математические ожидания.

Использование clickstream и исторического покупательского поведения как
разных групп предикторов согласуется с исследованием
[Van den Poel, Buckinx — Predicting online-purchasing behaviour](https://www.sciencedirect.com/science/article/pii/S0377221704002875).

## 21. Технические столбцы

| Столбец | Назначение | Риск | Production |
|---|---|---|---|
| `user_id` | соединение результата с пользователем | высокая кардинальность и запоминание пользователя | ⚠️ |
| `cutoff_date` | аудит даты среза | модель может выучить конкретный fold/сезон | ⚠️ |
| `target` | будущий GMV 30 дней | прямая утечка будущего | ⛔ |

В текущем ноутбуке `user_id`, `cutoff_date` и `target` исключаются из
`features`.

`user_id` допустим как ключ таблицы и для соединения предсказаний. Если
использовать его как категориальный признак, модель может запомнить таргеты
конкретных пользователей. Это может дать временную валидацию лучше, но плохо
переноситься на новых клиентов и требует отдельного эксперимента.

`cutoff_date` можно преобразовать в честные календарные признаки, если в
production заранее известна дата расчёта. Но при четырёх временных срезах
дерево легко переобучится на номер fold, поэтому исходная дата исключена.

## 22. Возможные утечки и смещения

### 22.1. Прямая временная утечка

Запрещено включать в признаки события после `cutoff`.

Правильно:

```text
features: event_date <= cutoff
target:   cutoff + 1 ... cutoff + 30
```

### 22.2. Ошибка на границе дат

Если день `cutoff` одновременно попадёт в признаки и target, появится прямая
утечка. В генераторе target начинается с `cutoff + 1`.

### 22.3. Неправильное объединение чанков

`sum` можно объединять сложением, но нельзя складывать:

```text
max, min, mean, std, median, nunique,
recency, last value, gaps, streaks
```

Исходный parquet отсортирован по `user_id, event_date`, но граница батча часто
разрезает одного пользователя. Генератор переносит последнего пользователя в
следующий батч и рассчитывает признаки только после получения его полной
истории.

Если убрать carry-over, значения recency, максимумов и регулярности станут
ошибочными, даже если код продолжит выполняться.

### 22.4. Утечка через глобальные статистики

В текущем генераторе нет target encoding, scaler, агрегатов по другим
пользователям или обученных BTYD-параметров.

Если они появятся позднее:

- обучать их только на train;
- для validation использовать состояние, полученное на train;
- для временных fold не использовать будущие таргеты;
- для target encoding применять out-of-fold/ordered схему.

### 22.5. Утечка через список пользователей

Срезы создаются для всех 250 000 `user_id`, встречающихся в полном исходном
файле. В рамках соревнования список пользователей заранее фиксирован, поэтому
это не даёт числовой информации о будущем GMV.

В реальном production будущие пользователи заранее неизвестны. Требуется
явная политика cold-start и создание строки пользователя из доступных на
момент `cutoff` данных.

### 22.6. Late-arriving events

Событие, приехавшее после расчёта, но имеющее старый `event_date`, изменяет:

- суммы;
- recency;
- интервалы;
- блоки;
- decay-признаки.

Production-конвейер должен зафиксировать watermark/SLA и одинаково строить
исторические train-срезы.

### 22.7. Сезонность и temporal drift

Target по месяцам различается. Особенно опасно подбирать параметры на одном
периоде и много раз смотреть независимый тест. Схема оценки должна оставаться
временной:

```text
train_1 + train_2 -> train_3 validation
после фиксации параметров:
train_1 + train_2 + train_3 -> test_for_us
финал:
все размеченные срезы -> competition_test
```

### 22.8. Прореживание и `recorded_days`

Если правила сохранения нулевых строк изменятся, признаки `recorded_days` и
`recorded_zero_days` могут отражать версию пайплайна, а не поведение клиента.
Их необходимо проверить отдельной ablation-валидацией.

## 23. Production-контракт

Чтобы использовать признаки в production, требуется обеспечить:

1. Данные доступны только до расчётного `cutoff`.
2. Дневная граница и часовой пояс совпадают с обучением.
3. Хранится не менее 270 дней истории либо корректно заполняются cold-start
   значения.
4. Один пользователь рассчитывается целиком; при распределённой обработке все
   его строки попадают в одну logical group.
5. Пропущенное событие и настоящее нулевое значение различаются одинаково в
   train и serving.
6. Для recency используется `271`, если события не было, и одновременно
   передаётся `never_* = 1`.
7. Все отношения используют `R(a, b)`, а не `clip(lower=1)`.
8. Late events обрабатываются по зафиксированной политике.
9. Версия формул и список признаков версионируются вместе с моделью.
10. `target` никогда не попадает в production feature store.

## 24. Что не включено намеренно

В генератор не включены:

- истинные BG/NBD/Gamma-Gamma predictions;
- target encoding по `user_id`;
- агрегаты с использованием target других пользователей;
- признаки из будущих 30 дней;
- полное заполнение отсутствующих дней отдельными строками;
- нормализация/scaling по всей выборке;
- медианы по всем дневным строкам каждого окна, кроме GMV покупочных дней за
  270 дней.

Причины: риск утечки, необходимость обучения только на train или высокая
стоимость памяти/вычислений.

## 25. Практическое использование

629 признаков — это feature pool, а не требование использовать каждый столбец
в финальной модели. После построения срезов рекомендуется:

1. Обучить LightGBM/CatBoost на полном наборе.
2. Сравнить importance только на временной validation.
3. Провести ablation по группам: окна, RFM, блоки, decay, воронка, регулярность.
4. Удалять признаки только по результату RMSLE, а не только по низкому gain.
5. Проверить стабильность выбранного набора на `test_for_us` один раз после
   фиксации решения.

Коррелирующие признаки могут делить importance неравномерно: один получает
высокий gain, а почти эквивалентный — ноль. Нулевая importance сама по себе не
доказывает вред признака.
